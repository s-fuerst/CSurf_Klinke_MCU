# Project Memory

## Decisions

- 2026-07-05: Windows build is driven from WSL via `scripts/build-windows.sh`. Key choices:
- 2026-07-05: **VS generator (MSBuild), NOT Ninja.** Ninja's stat-based dependency model breaks on the `\\wsl.localhost`/9P mount (CMake try-compile source shows up as "missing"); MSBuild tolerates the mapped drive. Generator auto-picked from the installed VS major version (16=2019, 17=2022; `MCU_VS_GENERATOR` overrides).
- 2026-07-05: **`pushd \\wsl.localhost\<distro>\...`** maps the repo UNC to a temp drive (Z:), so MSVC/rc.exe/juceaide read source straight off the WSL filesystem — no copy to /mnt/c.
- 2026-07-05: **Portable CMake 3.31.6** cached under `~/.cache/csurf-klinke-mcu/` (JUCE 8 needs >=3.22; VS2019 bundles 3.20).
- 2026-07-05: **`CMAKE_SUPPRESS_REGENERATION=ON`** silences MSB8064/65 regen-dependency warnings (unreliable over 9P); script always re-runs configure, so no cost.
- 2026-07-05: **build dir is `build_win/`** (multi-config VS generator → `build_win/Release|Debug/`), kept separate from the Linux `build/`. `.gitignore`d.
- 2026-07-05: `scripts/build-windows.sh` incremental model: the default (no flags) SKIPS the CMake configure step and only builds — configure runs once initially, or on `--clean`/`--reconfigure`. Rationale: configure is ~40s (re-runs the JUCE/juceide setup) and bumps the `VERSION.txt` build counter, so running it every build was wasteful and inconsistent with the Linux `cmake ..`-once / `cmake --build`-repeatedly model. `--reconfigure` is required after editing `CMakeLists.txt` or the source list (CMAKE_SUPPRESS_REGENERATION=ON means MSBuild will not auto-reconfigure).

- 2026-07-06: Channel model decisions (extender): (a) Offset field DROPPED — unit position is implicit = unitIndex*8 (no manual offset in config dialog; matches Option B). (b) Bank scroll = the WHOLE N*8 bank scrolls together via globalOffset (Channel Up/Down + track-selection-follow move the entire bank); matches Cockos original + linked-modes default. (c) Master fader = PER UNIT, not main-only — semantics of what each unit's master fader controls still OPEN (asked maintainer).
- 2026-07-06: Working assumption for channel indexing: flat strip index 1..N*8 across all units (so mode loops `channel=1..N*8` generalize trivially), master handled as a separate per-unit concept. Revisit if master semantics force otherwise.
- 2026-07-06: Master-slot semantics RESOLVED (extender): the 9th fader slot per unit is NOT architecturally special — the active MODE decides what each unit's master slot controls (Reaper master, dry/wet, folder master, …). In linked mode all N master slots coincide; in a future independent-mode world they can differ per unit. Consequence: the current "channel 0 = Reaper master" special-casing (getMediaTrackForChannel(0), OnFaderMove tid==8, FIXID id==8→-1) must move OUT of the core into mode logic (MultiTrackMode assigns unit 0's master slot → Reaper master to preserve current behaviour).
- 2026-07-06: Per-unit hardware reality (extender): each MCU unit = 8 FULL strips (fader + VPOT + select/mute/solo/rec + 2-line display) + 1 FADER-ONLY master slot (fader + touch only; NO VPOT/select/solo/mute/rec/display). So the master slot is constrained to fader-style control. Strips addressed flat 1..N*8; master slot is a separate per-unit concept.
- 2026-07-06: CORRECTION to earlier master-slot note: the master fader (channel 0) is ALREADY mode-defined today (MultiTrackMode→Reaper master, PlugMode→dry/wet via fader(channel==0), SendReceive→selected-track vol). FIXID macro in csurf_mcu.h is DEAD CODE (never expanded anywhere). OnFaderMove's tid==8→channel 0 is just physical→logical fader mapping (9th fader = master slot), not a Reaper-master binding. The only core-level master ref is Tracks::m_channelTracks[0]=CSurf_TrackFromID(0) (mixer default, benign). So NO 'move master special-casing out of core' refactor is needed — just expose one master slot per unit; modes decide meaning.
- 2026-07-06: Mackie SysEx device IDs confirmed (NicoG60/TouchMCU protocol doc): manufacturer 00 00 66; 0x14 = Mackie Control Universal/Pro (MAIN), 0x15 = MCU XT (EXTENDER), 0x10/0x11 = Logic Control/XT, 0x05 = HUI. Current code addHeader() already switches 0x14 (MCU) vs 0x15 (MCU_EX); PROX second-display uses non-standard 0x67 0x15. LCD cmd 0x12 = one 2x56 center LCD per unit (offset 0x00-0x37 upper line, 0x38-0x6F lower). Per-unit display addressing => DisplayHandler must be PER UNIT (own MIDI port + own device id), not one global.
- 2026-07-06: Per-unit config model (proposed, points 3+4 from maintainer): each unit = (MIDI in, MIDI out, EnumMCUType {MCU=main 0x14, MCU_EX=extender 0x15, PROX=QCon ProX main w/ 2nd 2x56 LCD}). This subsumes the existing GLOBAL CONFIG_FLAG_PROX (becomes per-unit PROX type). Main unit (MCU/PROX) owns transport + 7-seg timecode/assignment; extender (MCU_EX) = channel strips + its own center LCD only. EXACT display hardware of ProX vs extenders still TBD (asked maintainer).
- 2026-07-06: GENERALITY DECISION (extender config): the extension will be PUBLISHED, so per-unit config must support EVERY hardware combination — NOT a fixed EnumMCUType set. Each unit is described by INDEPENDENT capabilities: (MIDI in, MIDI out, SysEx device ID {0x14,0x15,...}, center-LCD panels {0,1,2}, has-transport+7seg {bool}). EnumMCUType {MCU,MCU_EX,PROX} survives only as dialog CONVENIENCE PRESETS that pre-fill the capabilities; a "custom" mode exposes them individually. (#LCD-panels=2 implies the ProX 2nd-panel path 0x67 0x15.)
- 2026-07-06: ORTHOGONALITY RULE (extender) — config position vs. global routing are INDEPENDENT axes: (a) config position of a unit = its CHANNEL-STRIP ORDER only (pos0→ch1-8, pos1→ch9-16,...), mirrors physical left→right; (b) GLOBAL routing (transport LEDs, SMPTE/7-seg timecode, assignment, automode LEDs, flip/globalview, drop, save/undo, metronome) goes to EVERY unit whose capabilities include transport+7seg, REGARDLESS of position. NO "topmost unit is the main" rule. A transport-capable unit can sit at any position; need ≥1 such unit. (Corrects an earlier wrong statement that Unit 0 = main.)
- 2026-07-06: PROTOCOL SCOPE narrowed (extender): HUI (0x05) and Logic Control (0x10/0x11) are OUT (HUI=different protocol; Logic Control never supported, never will). Only MCU-family device ids remain: 0x14 (main) / 0x15 (extender). Consequence: device id is NO LONGER an independent capability — it is DERIVED from the main/extender role. LCD panels ∈ {1,2} only (no displayless unit). Capability model collapses to TWO independent knobs: {isMain bool, lcdPanels 1|2}.
- 2026-07-06: DIALOG PRESETS = 4 named options forming the 2x2 grid {main,extender} x {1 LCD, 2 LCD}: Mackie Main / Mackie Extender / QCon ProX / QCon ProX extender. Internally store the 2 capabilities (preset = convenience). - 2026-07-06: QCon ProX extender = 2 LCDs CONFIRMED (maintainer). The 4 presets form a clean 2x2 grid {main,extender} x {1 LCD, 2 LCD}; all 4 are distinct. The 0x67 2nd-LCD path applies to any 2-LCD unit (main or extender). Per-unit capability model is now FULLY RESOLVED: (MIDI in, MIDI out, isMain, lcdPanels in {1,2}); device id derived (main=0x14, ext=0x15).

- 2026-07-06: NEW REQUIREMENT "release the extenders" (dynamic unit activation). - 2026-07-06: PERSISTENCE (extender, settled): two levels — (a) surface configString is Reaper-GLOBAL (not project), format changes 5-int → N×(in,out,isMain,model)+flags, legacy 5-int parses as 1 Mackie-main unit (WP-B); (b) project state is the <MCU_KLINKE> XML chunk in the .rpp, GUID-keyed per track + global Options/PlugMaps/CommandMode/Actions. Only anchor/q_channel are unit-count-sensitive (absolute slots 1..N*8); everything else (CommandMode VPOT idx 0-7, PlugMode slots/banks/pages, PlugMap offsets) is relative-within-8-block / FX-param-relative. Out-of-range anchor/q_channel = INACTIVE/hidden (never clamp-and-destroy), both on load AND at runtime (when active set shrinks via release feature). Add version="1" attr to XML root for migration. No per-unit project state for linked mode. Re-check per-mode when designing each mode for N units.
- 2026-07-07: WP-A (HardwareUnit) open questions ALL 6 RESOLVED (ai-docs/extender-wp-a-hardware-unit.md §9 now a decisions section): (1) Input indexing = GLOBAL — HardwareUnit knows m_unitIndex, adds offset, emits global channel 1..N*8; surface/modes never see local on input. (2) Master = logical channel 0 BROADCAST now — setFader(0)→all units' setMasterFader, any unit master move→fader(0); per-unit master deferred to independent-mode. (3) Hardware-state caches (faderPos[9], ledState, stateRec, ...) MOVE INTO HardwareUnit; CCSManager keeps only logical/mode state. (4) Display multiplexer = COMPOSITE MultiDisplay — mode holds a composite Display (IS-A Display) owning N real per-unit child Displays; changeField(row, globalField 1..N*8)→child[(f-1)/8].changeField(row,(f-1)%8+1); rows 2-3 (ProX) silently dropped on non-ProX units; per-unit DisplayHandler/Display stay byte-identical to today; modes change only field range + construction site (new Display(h,4)→createMultiDisplay(h,N)). Chose composite over CCSManager-router (keeps per-unit path untouched + modes own their display) and over modes-loop (avoids touching every mode's render now). (5) Multiple main units = ACCEPT redundancy (all fire, idempotent; no primary-main concept). (6) MIDI-open/JACK sequencing = open ALL N outputs, ONE 200ms usleep, reset all, start all inputs (200ms total, independent of N) — CAVEAT: PipeWire-JACK buffer race (MEMD 2026-06-27) only observed with 1 port; N-port variant UNVERIFIED, must test on real multi-unit hardware at WP-A integration; fallback = per-port 200ms (200ms×N).
- 2026-07-07: WP-A scope = N=1 extraction milestone ONLY (NOT an N-generic core). Hard numUnits()==1 invariant + ASSERT(globalChannel<=availableChannels()). The translation plumbing (unitForChannel/localOf/broadcastMasterFader/master-as-channel-0) is written N-generic, but N>1 CONSUMERS stay 1..8/global: CCSManager channel bounds+asserts, VPOT_LED[9], MeterBridge routing, ButtonManager per-note state, mode ProX-row logic. ## Bugs & Fixes

- 2026-07-05: `csurf_main.cpp` (line ~201): the macOS-port load-marker block (commit 4311da3) used `__attribute__((constructor))` + `/tmp/klinke_*.txt` writes. `__attribute__` is GCC/Clang-only — MSVC parses `constructor` as an undeclared identifier (errors C2065/C4430/C2062/C2143/C2447), blocking the Windows build. Wrapped the ctor block in `#if !defined(_WIN32)` (CRLF preserved via Python edit); macOS/Linux behaviour unchanged. The `/tmp/klinke_entry.txt` writes inside `REAPER_PLUGIN_ENTRYPOINT` are harmless no-ops on Windows (fopen fails, `if(f)` guards) and were left as-is. This scaffolding should eventually be cleaned up or gated behind `MCU_DEBUG_LOG`.
- 2026-07-06: DisplayHandler NULL pointer guard (2026-06-22, Rothchild fix #10): sendToHardware() dereferenced m_pActualDisplay without NULL check. When MIDI device init fails (no hardware / wrong device), m_pActualDisplay stays NULL → SIGSEGV on first PanMode::activate(). This was THE crash on "Add control surface → OK".
- 2026-07-06: a2jmidid LED bug (2026-06-23): a2jmidid converts Note On velocity 0 → Note Off (issue jackaudio/a2jmidid#14). MCU hardware ignores Note Off for LED control → LEDs never turn off and never blink. Fix: in SendMidi(), velocity 0x00 with Note-On status (0x90-0x9F) is mapped to 0x02; all direct m_midiout->Send(0x90,...) calls replaced with SendMidi(...); DropState::updateMCU() maps LED_OFF inline to 0x02. Affected: PROX devices with a2jmidid; the JACK-MIDI bridge is not affected.
- 2026-07-06: PipeWire-JACK startup crash (2026-06-27): SIGSEGV in process_empty, data-loop.0, pipewire-jack.c:1783. Triggered by our extension opening a JACK MIDI output port and sending MIDI before PipeWire finishes buffer allocation. PERMANENT FIX: Sleep(200ms) in CSurf_MCU constructor, after CreateMIDIOutput, before MCUReset(). linux=usleep(200000), win32=Sleep(). csurf_mcu.cpp.
- 2026-07-06: macOS configFunc crash (2026-07-04): SIGSEGV at 0x0. Root cause: swell-modstub-generic.cpp bound SWELL via SWELL_dllMain getfunc param, which REAPER passes as NULL on macOS. All SWELL function pointers remained NULL → DialogBox/CreateWindow dereferenced NULL. Fix: switched macOS build to swell-modstub.mm, which binds SWELL at dylib load via REAPER's NSApp delegate ([del swellGetAPPAPIFunc]).
- 2026-07-06: macOS case-insensitive APFS (2026-07-03): root-level project files collided with system headers — VERSION→<version> (libc++ parse error), Assert.h→<assert.h> (assert undeclared cascade). Fix: rename VERSION→VERSION.txt, Assert.h→McuAssert.h. The clang warning "non-portable path to file '<X>'; specified path differs in case" is the smoking gun. Watch for new root files.

## Patterns

- User can run sudo commands when requested — just tell them what to run and they'll execute it. No sudo password prompt needed from agent side.
- Version source = VERSION.txt file (repo root), NOT hard-coded. Format "<version> <build-count>". Bump version manually (reset count); count auto-increments per `cmake` configure. Generated build/Version.h → MCU_VERSION_STRING in csurf_mcu.h GetDescString. AGENTS.md §4 documents it.
- Deploy is the AGENT's job, not CMake's: after a successful Linux build, `cp build/reaper_csurf_mcu_klinke.so ~/.config/REAPER/UserPlugins/`. No CMake auto-deploy (keeps CI/Windows/macOS clean). Reaper needs full restart to reload.
- Logging architecture: MCU_DEBUG_LOG = standalone CMake OPTION (default ON), NOT tied to CMAKE_BUILD_TYPE → currently EVERY build logs, including Release. When OFF, MCU_LOG(...) compiles to ((void)0) (see src/core/McuDebugLog.h #else) → zero runtime cost. 16 call sites in 6 files; most verbose: sendToHardware logs every text write (ROW0/ROW1 snd). Release goal: default OFF, ON only for debug builds.
- Build-flow rule (always run both steps, otherwise no build-count increment): `cd build && cmake .. -DCMAKE_BUILD_TYPE=Release && cmake --build . -- -j$(nproc)`. The increment happens ONLY in the configure step (`cmake ..`), NOT in the build step. Running only `cmake --build` (incremental) without `cmake ..` first produces a build without an incremented counter. Mnemonic: "configure = increments, build = links".
- Commit messages always in English (user requirement).
- No commits without explicit user instruction (user requirement).
- Always write links out in full (https://...), not as Markdown hyperlinks [text](URL) — the user cannot click Markdown links.
- HIGH-PRIORITY LANGUAGE RULE: the dialog with the user may be in German, but EVERYTHING written into a file (source, comments, strings, logs, commit messages, docs, AGENTS.md, manual, MEMD.md, generated code, configs, scripts) MUST be in English. Never write German text into a file, not even comments. Anchored at the very top of AGENTS.md as "⚠️ Language rule (HIGH PRIORITY)".
- macOS case-insensitivity hazard: project files at repo root (on the -I path) collide case-insensitively with system headers on APFS. Found: VERSION→<version> (libc++), Assert.h→<assert.h>. The clang -Wnonportable-include-path warning ("differs in case from file name on disk") is the tell. Mitigation: unique file names (VERSION.txt, McuAssert.h). Watch for new ones whenever a new root-level header is added.
- Modern Boost needed for libc++/C++17: keep Boost ≥ 1.81 (we pin 1.91.0). Old Boost (1.39) requires heavy patching for modern compilers; not worth it.
- macOS build: NEVER set CC to Homebrew gcc — JUCE 8 juceaide needs Apple Clang. CMakeLists.txt forces Clang on Darwin. Override with -DCMAKE_C_COMPILER if ever needed.
- macOS JUCE event dispatch is automatic via NSRunLoop (driven by REAPER main thread); do NOT call dispatchNextMessageOnSystemQueue on macOS (no impl in JUCE 8). Linux/X11 needs the manual pump (#if JUCE_LINUX in csurf_mcu.cpp Run()).
- macOS SWELL stub: each platform has a DIFFERENT swell-modstub variant. macOS = swell-modstub.mm (NSApp delegate constructor), Linux = swell-modstub-generic.cpp (SWELL_LOAD_SWELL_DYLIB dlopens libSwell.so, OR non-dlopen path with SWELL_dllMain getfunc), Windows = none (native Win32). Never use the generic stub on macOS; REAPER does not pass the getfunc through SWELL_dllMain there.
- Portable Linux build gotchas (docker/release-linux.Dockerfile, all container-scoped): (1) JUCE 8 needs cmake ≥3.22 but Debian 11 ships 3.18 → install the cmake.org binary tarball. (2) juceaide (JUCE's codegen helper) is built by a RECURSIVE cmake subprocess whose PASSTHROUGH_ARGS does NOT include CMAKE_C[XX]_FLAGS — so forcing -I/usr/include/freetype2 via CMAKE_CXX_FLAGS does NOT reach juceaide. (3) juceaide compiles juce_graphics.cpp which needs <ft2build.h> (flat header under /usr/include/freetype2/) and <fontconfig/fontconfig.h>. Fix: symlink /usr/include/ft2build.h → freetype2/ft2build.h AND /usr/include/freetype → freetype2/freetype. Plus install libfontconfig1-dev. (4) Debian gcc enables -Wl,--as-needed by default → drops unused -l libs from NEEDED (X11 gets dropped; harmless — JUCE loads X11 via dlopen). (5) Need libxcursor/xinerama/xrandr/xrender/xcomposite-dev + libglu1-mesa-dev for JUCE pkg-config module deps. (6) Static libstdc++.a on Debian 11 is built with -fPIC, so -static-libstdc++ works for a SHARED lib.
- Subagent `output` path quirk: when a foreground subagent is given a relative `output` path (e.g. "ai-docs/foo.md"), the framework does NOT write it into the repo at that path — it nests it under `.pi-subagents/artifacts/outputs/<runId>/ai-docs/foo.md` instead (plus a copy at `.pi-subagents/artifacts/<runId>_<agent>_<index>_output.md`). If the artifact must live in the repo, `cp` it from the artifacts dir afterwards. Confirmed 2026-07-07 with the planner run.
- Subagent "needs attention (no observed activity for 60s)" notifications can be STALE: they race against run completion. A run that already returned its output inline is DONE (verify with `subagent status` → look for "exit 0 / completed") — do NOT resume/interrupt a finished run on this signal alone.
